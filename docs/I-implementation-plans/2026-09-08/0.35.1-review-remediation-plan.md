## Purpose

Turn the post-`0.35.0` repository review into a bounded patch-release campaign.
The release should correct the confirmed privileged-helper defect first, close
the validation gap that allowed it, and then apply the smallest compatible CI,
supply-chain, typing, and maintainability improvements that can be validated
without widening into new hardware support or a broad refactor.

The review baseline was healthy:

- BuildPython CI profile: **18/18 steps passed**;
- tests: **4,182 passed, 1 skipped**;
- coverage: **90.28% total**, with core at 90.36%, tray at 89.29%, and GUI at
  90.96%;
- architecture validation: **24 rules, 612 files, 0 findings**;
- Ruff, formatting, mypy, exception transparency, code hygiene, dead code,
  ShellCheck, and repository validation all passed.

This tracker therefore treats the privileged-helper mismatch as the only
confirmed user-facing bug. The remaining items are bounded hardening or
maintenance opportunities; they must not justify speculative behavior changes.

## Patch-release guardrails

1. Preserve all public commands in `pyproject.toml` and all on-disk config and
   profile formats.
2. Keep `sysfs-leds` kernel-first and capability-driven. Brightness-only sysfs
   devices remain valid.
3. Do not add or reclassify any USB ID or backend without separate hardware
   evidence.
4. Keep `/usr/local/bin/keyrgb-power-helper` as the polkit-authorized installed
   executable unless the policy, installer, uninstaller, and tests are updated
   atomically.
5. The root helper must remain narrowly limited to CPU power-policy files and
   recognized keyboard-lighting sysfs nodes. Do not generalize it into an
   arbitrary sysfs writer.
6. Add a failing regression test before or with every confirmed correction.
7. Do not lower coverage baselines, architecture rules, exception-transparency
   budgets, or hardware-access tripwires to make the release pass.
8. Work one tracker item at a time and record exact commands and results in the
   progress log.
9. New security automation must pin third-party GitHub Actions to immutable
   commit SHAs.
10. The final release must follow `docs/3-contributing/03-release_procedure.md`;
    package/changelog versions use `0.35.1`, while the Git tag uses `v0.35.1`.

## Conventions

- **Priority:** `P0` release correctness or a validation hole around privileged
  code; `P1` compatibility/security hardening; `P2` bounded maintainability.
- **Effort:** `S`, `M`, or `L`.
- **Status:**
  - `confirmed` — direct evidence establishes a defect or missing control;
  - `accepted` — improvement is approved but implementation has not started;
  - `active` — currently being implemented;
  - `monitoring` — code is complete but merged, release, or hardware evidence is pending;
  - `done` — implementation and required evidence are complete;
  - `deferred` — explicitly moved out of `0.35.1`, with rationale and a successor issue;
  - `blocked` — named evidence or dependency is unavailable.

## R351-01 — Align ITE 8297 privileged LED-name handling

### Evidence

`keyrgb/core/backends/sysfs/privileged.py::helper_can_apply_led()` accepts the
exact channel names `ite_8297:1`, `ite_8297:2`, and `ite_8297:3`. The installed
root helper's `_validate_led_name()` accepts only names containing
`kbd_backlight`, so the same three names terminate with
`Refusing non-keyboard LED`.

The review reproduced the contradiction directly:

```text
caller_accepts= True
helper_accepts=False 'Refusing non-keyboard LED'
```

### Correction contract

- The application-side predicate and installed helper must accept the same
  narrowly defined keyboard LED names.
- Accept only `ite_8297:[123]` in addition to the existing keyboard-backlight
  patterns; do not accept arbitrary `ite_*` or non-keyboard LEDs.
- Path separators, traversal, unexpected channel numbers, malformed suffixes,
  and resolved paths outside `/sys/class/leds` must still be rejected.
- Existing `rgb:kbd_backlight` and other validated `*kbd_backlight*` behavior
  must remain unchanged.
- The privileged path must apply the same clamping and brightness-last behavior
  as direct sysfs writes.

### Planned files

- `keyrgb/core/backends/sysfs/privileged.py`
- `system/bin/keyrgb-power-helper`
- `tests/core/backends/general/sysfs/test_sysfs_privileged_unit.py`
- `tests/core/power/test_power_helper_sysfs_roots_unit.py` or a nearest new
  helper-contract test module

### Acceptance criteria

- A contract test loads the real installed-helper source and compares its LED
  allowlist with `helper_can_apply_led()` for accepted and rejected examples.
- Exact ITE 8297 channels 1–3 pass both boundaries; channel 4 and traversal
  variants fail both.
- A sandboxed helper test proves the selected ITE channel writes only below the
  injected LED root while unprivileged, without touching real sysfs.
- Focused sysfs backend and helper tests pass.

### Disposition

Confirmed and corrected. The shipped helper now accepts only the exact
case-insensitive ITE 8297 channel names already accepted by the application.
Contract tests compare both allowlists for valid, malformed, traversal, and
non-keyboard names. Investigation also found that the ITE 8297 direct color path
had no escalation route: a denied channel write now falls back through one
brightness-only helper call for that exact channel and propagates the original
failure when the helper is unavailable. Sandboxed tests verify per-channel
scaling, clamping, isolation, and rejection behavior. No live ITE 8297 hardware
was available, so hardware confirmation remains optional release evidence rather
than a new validation claim.

## R351-02 — Bring the installed Python helper under the quality gates

### Evidence

`system/bin/keyrgb-power-helper` is extensionless Python. Coverage is configured
with `source = ["keyrgb"]`, and the standard application scanners primarily
target `.py` files. The helper contains broad exception catches that are absent
from the reported zero-debt exception baseline. Existing tests load selected
helper behavior, but the caller/helper allowlist drift still passed all 18 CI
steps.

### Implementation approach

Choose the smallest design that makes the shipped helper an explicit validation
target. Preferred options, in order:

1. keep the installed executable path stable but maintain its implementation in
   an importable `.py` source with a thin generated or copied wrapper; or
2. explicitly teach Compile, Ruff, mypy where practical, coverage, code hygiene,
   and exception-transparency steps to scan the extensionless Python file.

Do not duplicate a third copy of helper policy. If application and helper code
cannot share runtime imports because the root helper must remain standalone,
enforce parity with a test that loads the exact shipped source.

### Acceptance criteria

- Syntax errors in the installed helper fail BuildPython Compile.
- Lint violations and new unannotated broad catches in the helper fail the
  relevant quality gate.
- Helper tests contribute measurable coverage, or the report separately exposes
  helper coverage with a non-regression threshold.
- The helper's intentionally best-effort catches use the smallest real exception
  set; required non-fatal boundaries are explicit and diagnostic.
- Tests prove that installer and polkit paths still reference
  `/usr/local/bin/keyrgb-power-helper`.
- Step 19 and the full CI profile pass after the change.

### Disposition

Confirmed and corrected without moving or coupling the standalone root helper.
BuildPython now passes the exact extensionless helper to Compile, Ruff, Ruff
Format, mypy, Code Hygiene, Exception Transparency, Dead Code, and Coverage.
Repo Validation fails closed if the shipped helper/polkit files disappear or any
application, installer, uninstaller, or polkit consumer drifts from
`/usr/local/bin/keyrgb-power-helper`.

The helper is executable in the source tree, has no broad exception catches or
silent best-effort writes, and fails closed when LED path resolution fails.
Coverage now measures it explicitly at 63.89% with a dedicated 60% per-file
floor; existing total, prefix, and watch-file thresholds were not lowered.

- Evaluate the current stable Python version above 3.13. Either add it to CI and

  imply tested support accidentally.
- Keep the mypy language floor at 3.10 unless a concrete typing incompatibility
  requires a separately justified change.
- Wheel/resource smoke remains green on the quality job.
- README or contributor support wording matches the final tested matrix.

3.10 through 3.14. The quality job remains on Python 3.12, the package minimum
remains `>=3.10`, and mypy retains its 3.10 language floor. Living CI and
contributor documentation distinguish those three contracts explicitly.

Fresh Python 3.14.7 validation installed every runtime/development dependency,
passed Pip Check, imported all required modules, and passed the complete test
suite and coverage gate. The normal Python 3.13 CI profile remained green.

## R351-04 — Add dependency and supply-chain automation

### Evidence

The release workflow pins GitHub Actions to immutable SHAs and publishes an
AppImage SHA-256 sidecar, which are strong existing controls. The review found
no Dependabot/Renovate configuration, scheduled dependency vulnerability audit,
CodeQL-equivalent scan, or release SBOM. Runtime and development dependencies
are lower-bounded rather than lockfile-reproducible.

### Minimum `0.35.1` scope

- Add Dependabot or an equivalent automated update configuration for Python and
  GitHub Actions.
- Add a reproducible dependency vulnerability audit to CI or a scheduled
  workflow. Define how temporary advisory-service failures differ from actual
  vulnerability findings.
- Give workflows the minimum explicit token permissions they need; the normal CI
  workflow should be read-only.
- Pin every newly introduced action to an immutable commit SHA.

### Follow-up-capable scope

- Generate an SBOM for the released AppImage and attach it to the GitHub Release.
- Evaluate artifact attestations or signatures in addition to checksums.
- Decide whether a release constraints/lock input is appropriate for AppImage
  reproducibility without forcing end-user source installs onto stale pins.

If an SBOM, attestation, or release lock cannot land safely in `0.35.1`, record a
named successor issue before marking this item done; the minimum scope remains a
release gate.

### Acceptance criteria

- Automation configuration parses and runs successfully in GitHub Actions.
- A known-vulnerable fixture or tool exit-code test proves findings fail the
  audit rather than being silently ignored.
- No workflow gains write permissions outside the release job.
- Contributor/release documentation names the audit and how to reproduce it.

### Disposition

Accepted and completed for the `0.35.1` minimum scope. Dependabot now checks
Python and GitHub Actions dependencies weekly. CI is explicitly read-only, and
the release workflow grants `contents: write` only to its AppImage publication
job. Both CI quality and release run an exactly pinned `pip-audit` wrapper before
their buildpython profiles.

The wrapper audits runtime requirements from `pyproject.toml`, not arbitrary
ambient packages. It fails with distinct exits for findings (`1`) and
tool/advisory/resolution failures (`2`); hermetic fixtures prove a known
vulnerability cannot be reported as clean. The audit script is included in the
recurring Ruff, Ruff Format, and mypy quality surfaces.

**Named successor issue R351-SC-01 — Release provenance and reproducibility
hardening:** evaluate an AppImage SBOM, artifact attestations or signatures,
CodeQL-equivalent scanning, and a release-only constraints/lock strategy. Those
controls require artifact-format and update-policy decisions beyond the safe
`0.35.1` remediation boundary.

## R351-05 — Make current-release AppImage checksum handling fail closed

### Evidence

The release workflow always publishes `keyrgb-x86_64.AppImage.sha256`, but
`verify_downloaded_sha256()` treats a missing tool, missing sidecar, or empty
sidecar as non-fatal unless users set `KEYRGB_REQUIRE_CHECKSUM=1`. This preserves
old releases but weakens the default contract for current releases that promise
the sidecar.

### Correction contract

- A newly resolved/current release that is expected to publish a checksum must
  fail closed if the checksum tool or sidecar is unavailable or malformed.
- A hash mismatch remains fatal and removes the downloaded image.
- Preserve an explicit, documented compatibility path for historical releases
  that predate sidecars. Do not silently classify an unknown current release as
  historical.
- Validate the sidecar as one SHA-256 digest rather than accepting arbitrary
  first-field text.
- Keep downloads atomic and remove incomplete or rejected artifacts.

### Planned files

- `scripts/lib/common_core.sh`
- `scripts/lib/user_integration.sh`
- nearby installer tests under `tests/installer/`
- `README.md` and/or `docs/2-usage/setup.md`

### Acceptance criteria

- Tests cover valid checksum, mismatch, missing sidecar, malformed digest,
  missing `sha256sum`, current release, historical compatibility, and explicit
  override behavior.
- Installer sandbox tests and ShellCheck pass.
- User-facing output clearly distinguishes integrity failure from download
  failure.

### Disposition

Accepted and completed. AppImage checksum verification now receives the exact
resolved or requested release tag and fails closed by default. Current releases,
prereleases, mutable or unknown refs, missing tools or sidecars, malformed
sidecars or hash output, and mismatches all remove the rejected download and
emit a distinct integrity-verification failure.

Compatibility is limited to canonical stable tags before `v0.23.4`, the first
release that published sidecars. Those historical tags alone may continue with
a warning when the sidecar or `sha256sum` is unavailable; a present but invalid
sidecar still fails. `KEYRGB_REQUIRE_CHECKSUM=1` forces strict verification for
historical tags and cannot be used to weaken current-release handling.

## R351-06 — Hold or reduce measured complexity without broad refactoring

### Evidence

The reviewed runtime contains approximately 78,832 Python lines across 513
files. BuildPython reported 35 LOC-monitor files, 7 waived files, and 13 long
import-block warnings. The runtime also contains 118 `type: ignore` annotations.
The largest application files include the 711-line Lenovo chassis protocol table
and the 695-line `PowerManager` facade.

### Patch-release approach

- Treat the existing metrics as non-regression budgets for `0.35.1`.
- Review each file touched by R351-01 through R351-05 for owner-local extraction;
  do not start an unrelated repository-wide cleanup.
- Keep data-heavy protocol tables cohesive when splitting would scatter
  hardware evidence.
- For `PowerManager`, extract only if another required change would otherwise
  add orchestration or policy logic to the facade.
- Audit new or touched `type: ignore` annotations and replace them with protocols
  or narrow casts where local and low risk.

### Acceptance criteria

- `0.35.1` does not increase LOC-monitor, waiver, long-import, broad-exception,
  or actionable dead-code counts.
- Any new waiver includes a concrete owner and reason; baseline inflation without
  implementation evidence is forbidden.
- The final progress log records whether the two largest files were retained or
  changed and why.

### Disposition

Accepted and completed as a non-regression review; no broad refactor was
justified. The merged `0.35.1` remediation state retains the review baselines of
35 LOC-monitor files, 7 LOC waivers, and 13 long-import warnings, with zero
actionable dead-code or active broad-exception findings. No baseline or waiver
was added, and the touched diff removes one `type: ignore` without introducing
another.

The 711-line ITE 8258 per-key/chassis protocol table was retained unchanged
because its existing waiver records that splitting cohesive product-variant
packet data would scatter hardware evidence. The 695-line `PowerManager` facade
was also retained unchanged because no remediation item added policy or
orchestration there; its methods remain thin delegates after the prior
battery-saver extraction. The temporarily over-threshold checksum test was
reduced to 300 lines before closeout rather than increasing the monitor count.

## R351-07 — Tighten the backend device protocol's untyped payload surface

### Evidence

`KeyboardDevice` strongly names the backend operations but leaves `set_color`,
`set_key_colors`, and `set_effect` payload and return annotations incomplete.
The codebase compensates with dynamic compatibility seams and localized
`type: ignore` annotations.

### Bounded scope

- Introduce shared color/key-map/effect payload aliases or focused protocols only
  where they describe every validated backend honestly.
- Preserve duck-typed test fakes and backend-specific effect dictionaries.
- Do not redesign the backend API or force brightness-only devices to claim RGB
  operations they do not support.

### Acceptance criteria

- Touched `KeyboardDevice` methods have explicit argument and return types.
- Mypy remains green across core, tray, GUI, and affected tests.
- No backend capability is inferred from method presence alone; `backend_caps`
  remains authoritative.
- If the change proves too broad for a patch release, record the exact blockers
  and successor issue, then mark this item `deferred` rather than partially
  typing incompatible backends.

### Disposition

Deferred without a partial protocol edit. Two independent implementation reviews
found that KeyRGB currently has two divergent keyboard-device protocols, roughly
ten untyped concrete device implementations, and payload contracts that differ
materially by backend. In particular, effect payloads legitimately include
backend-specific mappings, tuples/lists, scalar names or indices, and bytes;
per-key maps use tuple, integer, string, and virtual-zone keys. A narrow common
alias would be inaccurate, while a wide `object`-equivalent union would not
reduce the debt.

The honest return contract is `None` for production devices, but the effects
proxy intentionally preserves arbitrary fake return values in tested behavior.
Changing that contract, unifying both protocols, annotating every implementation,
and adding scoped `disallow_untyped_defs` enforcement is broader than a safe patch
release. Capability gating remains unchanged and authoritative through
`backend_caps`; brightness-only sysfs devices are not made to claim RGB support.

**Named successor issue R351-TYPE-01 — Unify and enforce keyboard device payload
protocols:** establish canonical RGB, key-map, and backend-specific effect payload
types; reconcile proxy return semantics; annotate every concrete backend and
relevant fake; and add scoped mypy enforcement in one coordinated change.

## R351-08 — Improve distro/install smoke confidence

### Evidence

CI runs on Ubuntu while Fedora/Nobara and Arch/CachyOS are the primary documented
installer targets. Existing installer sandbox and AppImage smoke tests are
strong, but they do not exercise a live desktop compositor, real polkit, or the
documented distro-family package paths.

### Bounded scope

- Add at least one non-Ubuntu container or sandbox smoke for distro detection and
  non-privileged installer planning, prioritizing Fedora or Arch.
- Keep privileged `/etc`, udev reload, polkit, and live hardware operations
  mocked or explicitly opt-in.
- Record manual AppImage launch evidence on one primary supported distro if
  available; lack of hardware must not be replaced by an unsupported support
  claim.

### Acceptance criteria

- Distro smoke cannot install packages or modify the host.
- Existing default hardware tripwires remain enabled.
- README distro status remains evidence-based.
- If CI cost or runner limitations block this item, create a named follow-up and
  retain the existing Ubuntu matrix without weakening it.

### Disposition

Accepted and completed with host-safe sandbox coverage rather than a new runner
or container. An internal `/etc/os-release` path seam keeps production behavior
unchanged while tests parse isolated Fedora and Arch fixtures through the real
distro-detection code. The smoke verifies the tested status labels and `dnf` or
`pacman` planning while tripwires forbid package-manager execution, `sudo`,
udev/polkit commands, hardware tools, and writes to host integration paths.

The normal pytest hardware-disable and tripwire environment remains explicit.
README continues to label Fedora/Nobara and Arch/CachyOS as tested, Debian/Ubuntu
as experimental, and openSUSE/other as best-effort. No live compositor, real
polkit, udev reload, AppImage GUI launch, or hardware was exercised, so this item
creates no broader distro or hardware-support claim.

### Hardware acceptance

one real `ite_8297:[123]` brightness/color application and confirm diagnostics
still select `sysfs-leds`. If unavailable, state clearly that acceptance is
sandbox/contract-test evidence only; do not delay the correctness fix or label
new hardware as validated.

### Publication checklist

1. Run `./scripts/release/version.sh 0.35.1`.
2. Complete `CHANGELOG.md` under `## 0.35.1 (YYYY-MM-DD)`.
3. Run the release profile again after the version change.
4. Commit and push `main` first.
5. Verify local and remote tag absence and that `origin/main` matches `HEAD`.
6. Create and push only the explicit `v0.35.1` tag.
7. Verify the GitHub Release contains the AppImage and matching `.sha256`

### Disposition

Monitoring at the publication boundary. The final uncommitted candidate passed
the focused AppImage tests, targeted mypy, exception-transparency Step 19, the
live dependency audit, `git diff --check`, and every executed release-profile
step. The release profile reported 4,309 tests passing, 1 skipped, 90.12% total
coverage, 35 LOC-monitor files, 7 waivers, and no actionable architecture,
dead-code, hygiene, or broad-exception findings.

The release AppImage was rebuilt after replacing hardcoded Tcl/Tk 8.6 paths with
interpreter-derived exact-version native libraries and stable bundled script
paths. A native extracted-artifact smoke passed with Tcl 9.0.3, `_tkinter`, the
tray-icon import, diagnostics JSON, and checksum verification. The required
minimal-container smoke remains unverified because neither Docker nor Podman is
available on the validation host; the release profile therefore completed 19
of 20 steps with that one step skipped.

No live ITE 8297 hardware, compositor, polkit, or udev reload was exercised, so
hardware acceptance remains sandbox/contract-test evidence only. The candidate
is not yet ready to version: it still requires authorization to commit, final
validation from a clean committed tree, resolution or explicit acceptance of
the unavailable container smoke, release-note/version updates, and the
publication checklist above.

## Recommended implementation order

1. **R351-01:** lock the failing cross-boundary contract in tests and correct the
   allowlist mismatch.
2. **R351-02:** make the shipped helper visible to quality gates so the same
   class of drift cannot recur.
3. **R351-03:** expand the supported Python evidence and align metadata.
4. **R351-04 and R351-05:** add supply-chain automation and tighten current
   release integrity handling.
5. **R351-06 through R351-08:** take only bounded, non-disruptive improvements;
   defer with explicit successor issues when patch risk exceeds benefit.
6. **R351-09:** run merged validation, version, publish, and verify artifacts.
